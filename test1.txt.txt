# DSE DevOps - Code Readability & Pipeline Validation Guide

## 1. Overview

This document establishes coding standards, validation procedures, and best practices for DSE DevOps team members working with Jenkins Pipelines, Shared Libraries, and automation scripts.

---

## 2. Code Readability Standards

### Naming Conventions
- **Variables**: Use camelCase (`fortifyApiToken`, `pendingJobCount`)
- **Functions**: Use descriptive verbs (`getFortifyPendingJobsCount`, `notifyTeamsChannel`)
- **Files**: Use lowercase with hyphens (`fortify-notification.groovy`)

### Code Structure
- Add comments for complex logic blocks
- Use consistent indentation (4 spaces)
- Keep functions under 50 lines where possible
- Group related variables together

**Example:**
```groovy
// Good
def fortifyApiToken = envProperty.fortify_api_credential_id
def fortifyApiURL = envProperty.fortify_api_url
def pendingJobThreshold = envProperty.fortify_count_threshold as Integer

// Bad
def x = envProperty.fortify_api_credential_id
def url123 = envProperty.fortify_api_url
```

---

## 3. Pipeline Validation Steps

### Step-by-Step Validation Process

**Step 1: Create Feature Branch**
```bash
git checkout -b feature/your-feature-name
```

**Step 2: Local Syntax Check**
```bash
# For Groovy files
groovy -cp . yourScript.groovy --compile-only
```

**Step 3: Use Test Repositories**
- **DO NOT** validate in production repositories
- Use designated test repositories:
  - `dse-devops-test-pipeline`
  - `dse-sandbox-app`
  - `dse-validation-project`

**Step 4: Test Build Configuration**
- **Build Type**: Use `freestyle` or `pipeline` test jobs
- **Branch**: `feature/*` or `test/*` branches only
- **Jenkins Instance**: Use `jenkins-dev.company.com` (NOT production)

**Step 5: Run Validation Build**
```groovy
// In Jenkinsfile
pipeline {
    agent any
    stages {
        stage('Validate') {
            steps {
                sh 'echo "Running validation..."'
                // Your validation logic
            }
        }
    }
}
```

**Step 6: Code Review & Merge**
- Create Pull Request
- Require 2 approvals minimum
- Merge to `develop` → then `main`

## 5. DOs and DON'Ts

### ✅ DOs

| Practice | Example |
|----------|---------|
| Use descriptive variable names | `def pendingJobThreshold` |
| Add comments for complex logic | `// Reset notification state after success` |
| Validate in test repositories | `dse-devops-test-pipeline` |
| Use feature branches | `feature/fortify-notification` |
| Enable test mode for notifications | `call(testMode: true)` |
| Handle errors gracefully | `try { ... } catch (e) { ... }` |
| Use credentials from Jenkins | `withCredentials([...])` |
| Log important steps | `println "INFO: Threshold exceeded"` |

### ❌ DON'Ts

| Practice | Why It's Wrong |
|----------|----------------|
| Test in production repositories | Risk of impacting live systems |
| Hardcode credentials | Security vulnerability |
| Skip code reviews | Reduces code quality |
| Use generic variable names (`x`, `temp`) | Reduces readability |
| Send test notifications to production channels | Creates false alerts |
| Commit directly to `main` branch | Bypasses validation |
| Use `sleep()` for synchronization | Inefficient, unreliable |
| Ignore error handling | Causes silent failures |

## 2. Code Readability Standards

### Naming Conventions
- **Variables**: Use camelCase (`fortifyApiToken`, `pendingJobCount`, `mockCount`)
- **Functions**: Use descriptive verbs (`getFortifyPendingJobsCount`, `notifyTeamsChannel`, `updateGlobalCounter`)
- **Files**: Use lowercase with hyphens (`fortify-notification.groovy`)

### Code Structure
- Add comments for complex logic blocks
- Use consistent indentation (4 spaces)
- Keep functions under 50 lines where possible
- Group related variables together

**Example:**
```groovy
// Good
def fortifyApiToken = envProperty.fortify_api_credential_id
def fortifyApiURL = envProperty.fortify_api_url
def pendingJobThreshold = envProperty.fortify_count_threshold as Integer

// Bad
def x = envProperty.fortify_api_credential_id
```

## 3. Pipeline Validation Steps

### Step-by-Step Validation Process

**Step 1: Identify Application Repository**
- Use the **actual application repository** that your change will impact
- DO NOT use generic test repositories for application-specific changes
- Example: If validating Fortify notification for `ecom-api`, use `ecom-api` repository

**Step 2: Create Appropriate Branch**

For **DEV Pipeline:**
```bash
git checkout -b feature/your-story-id-description
# Example: feature/DSE-1234-fortify-notification
```

For **PROD Pipeline:**
```bash
git checkout -b hotfix/your-story-id-description
# Example: hotfix/DSE-1234-fortify-notification-fix
```

**Important Notes:**
- DSE team creates branches as per story assignments
- We **DO NOT** use `develop` branch for validation
- Branch naming follows: `feature/*` for dev, `hotfix/*` for prod

**Step 3: Create POC Jenkins Job**

Create a separate POC job for testing (DO NOT modify production jobs):

**Job Naming Convention:**
- Dev: `ecom-api-dev-poc-fortify-test`
- Prod: `ecom-api-prod-poc-fortify-test`

**Step 4: Configure POC Job with Test Parameters**

Add parameters to control testing scenarios:

```groovy
properties([
    parameters([
        choice(
            name: 'SCENARIO',
            choices: ['FAILURE', 'SUCCESS', 'NORMAL'],
            description: 'Choose POC scenario'
        ),
        string(
            name: 'MOCK_COUNT',
            defaultValue: '0',
            description: 'Simulated fortifyScanCount for testing'
        ),
        booleanParam(
            name: 'ENABLE_NOTIFICATION',
            defaultValue: false,
            description: 'Enable Teams notification (keep false during testing)'
        )
    ])
])
```

**Step 5: Test Only Required Stages**

You don't need to include all stages - only the ones you're testing:

```groovy
node(env.dse_worker_node) {
    ansiColor('xterm') {
        try {
            println "============== POC TEST START =============="
            println "Selected Scenario       : ${params.SCENARIO}"
            println "Mock Fortify Count      : ${params.MOCK_COUNT}"
            println "Notification Enabled    : ${params.ENABLE_NOTIFICATION}"
            println "============================================="
            
            def mockCount = params.MOCK_COUNT as Integer
            
            // Only include stages you need to test
            stage('POC: Run Scenario') {
                if (params.SCENARIO == 'FAILURE') {
                    println "POC → Simulating FAILURE scenario"
                    updateGlobalCounter("runCheck", mockCount)
                    error("Simulated failure for POC testing")
                } else if (params.SCENARIO == 'SUCCESS') {
                    println "POC → Simulating SUCCESS scenario"
                    updateGlobalCounter("resetWithoutNotification")
                } else {
                    println "POC → Simulating NORMAL scenario"
                    updateGlobalCounter("runCheck", mockCount)
                }
            }
            
            println "POC Completed Successfully"
            
        } catch (err) {
            println "=========== FAILURE HANDLING BLOCK ==========="
            println "Build failed → Executing failure logic"
            def mockCount = params.MOCK_COUNT as Integer
            updateGlobalCounter("runCheck", mockCount)
            throw err
            
        } finally {
            println "=========== FINALLY BLOCK EXECUTED ==========="
            
            // Conditional notification based on parameter
            if (params.ENABLE_NOTIFICATION) {
                println "Sending Teams Notification"
                sendTeamsNotification()
            } else {
                println "Notification DISABLED for testing"
            }
            
            println "============== POC TEST END =============="
        }
    }
}
```

**Step 6: Test in Both DEV and PROD Regions**

Create separate POC jobs for each environment:

| Environment | POC Job Name | Branch Type | Purpose |
|-------------|--------------|-------------|---------|
| DEV | `ecom-api-dev-poc-notification` | `feature/*` | Test dev pipeline changes |
| PROD | `ecom-api-prod-poc-notification` | `hotfix/*` | Test prod pipeline changes |

Test scenarios in both jobs to ensure consistency across environments.

**Step 7: Validation Complete - Cleanup**

After successful testing:
- Delete POC Jenkins jobs
- Delete test branches (if not needed)
- Merge validated changes to appropriate branch
- Enable notifications in production

## 4. Testing Changes with External Notifications

### ⚠️ CRITICAL: Disable Notifications During Testing

**Problem:** Teams channels with leads and application team members receive false alerts during testing.

**Solution:** Always disable notifications during validation phase.

### Option 1: Use Boolean Parameter (Recommended)
```groovy
properties([
    parameters([
        booleanParam(
            name: 'ENABLE_NOTIFICATION',
            defaultValue: false,
            description: 'Enable Teams notification (keep FALSE during testing)'
        )
    ])
])

// In your notification function
def sendTeamsNotification() {
    if (!params.ENABLE_NOTIFICATION) {
        println "INFO: Notification DISABLED for testing"
        return
    }
    
    // Actual notification logic
    notifyTeamsChannel()
}
```

### Option 2: Hardcode Notification Disable in POC Job
```groovy
// In POC job - explicitly disable notifications
def notificationEnabled = false  // Hardcoded for POC

if (notificationEnabled) {
    sendTeamsNotification()
} else {
    println "Notifications disabled for POC testing"
}
```

### Option 3: Use Test Scenario Parameters
```groovy
properties([
    parameters([
        choice(
            name: 'SCENARIO',
            choices: ['FAILURE', 'SUCCESS', 'NORMAL'],
            description: 'Test scenario'
        ),
        booleanParam(
            name: 'SEND_NOTIFICATION',
            defaultValue: false,
            description: 'Send actual notification (enable only after testing complete)'
        )
    ])
])

finally {
    if (params.SEND_NOTIFICATION) {
        sendTeamsNotification()
    } else {
        println "Notification skipped - testing mode"
    }
}
```

### Testing Workflow

**Phase 1: Initial Testing (Notifications DISABLED)**
1. Create POC job with `ENABLE_NOTIFICATION = false`
2. Test all scenarios: FAILURE, SUCCESS, NORMAL
3. Verify logic without sending actual notifications
4. Check console logs for expected behavior

**Phase 2: Final Validation (Notifications ENABLED)**
1. After confirming logic is correct
2. Change `ENABLE_NOTIFICATION = true`
3. Run ONE final test to verify notification is sent correctly
4. Immediately disable notifications again

**Phase 3: Production Deployment**
1. Merge changes to production
2. Enable notifications in production Jenkins jobs
3. Monitor first few real notifications

```groovy
            handleBuildFailure(err)
            
        } finally {
            if(currentBuild.result == 'FAILURE') {
                handleFailure()
            }
            sendTeamsNotification()
        }
    }
}
```

## 10. Common Pitfalls & Solutions

### Pitfall 1: Testing in Production Job
**Problem:** Modifying production Jenkins job for testing  
**Solution:** Always create separate POC job

### Pitfall 2: Using Wrong Repository
**Problem:** Using generic test repository instead of actual app repo  
**Solution:** Use the application repository your change impacts

### Pitfall 3: Notifications Not Disabled
**Problem:** Sending test notifications to production Teams channels  
**Solution:** Use `ENABLE_NOTIFICATION = false` parameter

### Pitfall 4: Only Testing in DEV
**Problem:** Not validating changes in PROD environment  
**Solution:** Create and test POC jobs for both DEV and PROD

### Pitfall 5: Copying Entire Pipeline
**Problem:** Including all stages in POC job unnecessarily  
**Solution:** Only include stages you're testing

### Pitfall 6: Forgetting to Enable Notifications in Production
**Problem:** Changes deployed but notifications don't work  
**Solution:** After validation, enable notifications in production
